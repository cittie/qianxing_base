# 平台适配层

基座 = **抽象层**（`design/`）+ **平台适配层**（`platforms/`）+ **通用工具**（`tools/`）。

- `design/` 里的东西**不依赖任何平台**；
- **每个目标平台在 `platforms/<name>/` 里有一份自己的说明与专属工具**；
- 换平台时改的是这一层，**不是**抽象层。

> 📌 **原则**：平台专属的一切（词汇、上限、规则、工具、数据源）都放 `platforms/<name>/`，
> 不要混进 `design/` 或 `tools/`。若某能力**两个以上平台都需要**，再把它上移到 `tools/`。
> 反过来说，**平台工具放基座是正确的** —— 它们在基座里按平台隔离，游戏侧通过显式路径调用。

## 每个平台至少要回答的问题

| # | 问题 | 为什么重要 |
| --- | --- | --- |
| 1 | **输入方式**与操作强度上限（键鼠 / 手柄 / 触屏；是否需要精细操作） | 决定「软保障」原则能否落地 |
| 2 | **硬性上限**（同屏实体数 / 节点数 / 每次命中目标数 / 定时器数…） | 数值与关卡规模要按**最紧的那个平台**设计 |
| 3 | **事件与生命周期模型**（有哪些事件、能否挂载、触发时机） | 架构里的逻辑层能不能原样搬过去 |
| 4 | **存档与数据**（能否读写、格式、是否跨设备） | 影响 meta 进度设计与调参工具 |
| 5 | **发布与分成**渠道 | 影响宣发计划与收益模型 |
| 6 | **合规约束**（内容红线、能否搬运、第三方工具边界） | 🚫 **一票否决项** —— 先查再动手 |
| 7 | **本地工具链**（SDK / 编辑器 / 语言版本 / 调试方式） | 决定自动化与测试能到什么程度 |
| 8 | **平台专属工具**（放本目录 `tools/`） | 与其它平台隔离，避免互相污染 |

## 平台与抽象层怎么对接

`design/architecture.md` 把实现分成三层（逻辑 / 表现 / 平台接口），**只有第三层随平台变**：

```
L1 逻辑层   ← 各平台共用（数值、规则、状态机）
L2 表现层   ← 各平台各写（UI、特效、镜头）
L3 平台接口 ← 就是 platforms/<name>/ 里描述的那些东西
```

所以本目录的每一份平台说明，**本质上是在填 L3 的那张表**。
